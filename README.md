# My API — основа будущего продукта

Проект начинался как учебное приложение, чтобы разобраться, как устроено
современное веб-API на Python. Сейчас он превращается в продукт: сервис
аналитики клиентской базы для небольшого бизнеса.

**Три документа и зачем каждый:**

| Файл | О чём |
|---|---|
| `README.md` (этот) | как устроено приложение и как его запустить |
| `ROADMAP.md` | что за продукт мы строим, в каком порядке и почему именно так |
| `TASKS.md` | конкретные задачи с отметками о прогрессе — **что делать сегодня** |

Внутри: **FastAPI**, **SQLAlchemy** (асинхронно) + **PostgreSQL**, **Poetry** и **Docker**.
Приложение запускается одной командой и умеет:

- показывать страницу «Hello World» на `http://localhost:8000/`;
- регистрировать пользователей (с почтой) и выдавать токен при входе;
- отдавать защищённые эндпоинты: `/users/me` и список `/users`;
- различать роли `user` / `admin` и не пускать обычного пользователя
  на административные действия;
- поднимать схему базы через **Alembic** (не через `create_all`);
- прогонять тесты регистрации и входа командой `pytest`.

## 1. Быстрый старт

Нужен только установленный **Docker Desktop**. Больше ничего ставить не надо
(ни Python, ни PostgreSQL) — всё поднимается внутри контейнеров.

```bash
# из папки my_api
docker compose up --build
```

Дождись строки вида `Application startup complete` и открой в браузере:

- `http://localhost:8000/` — страница **Hello World**;
- `http://localhost:8000/hello` — то же самое, но в виде JSON;
- `http://localhost:8000/docs` — **интерактивная документация** (Swagger UI),
  где можно нажимать кнопки и вызывать методы API прямо из браузера.

Остановить: `Ctrl+C`, затем при желании `docker compose down`.

> Если установлен `make`, можно короче: `make up`, `make logs`, `make down`.

## 2. Что такое каждая технология (простыми словами)

| Технология | Зачем нужна |
|------------|-------------|
| **FastAPI** | Фреймворк для создания API. Мы описываем «функции-обработчики», а он превращает их в веб-эндпоинты и сам делает документацию. |
| **Uvicorn** | Сервер, который запускает FastAPI-приложение и принимает HTTP-запросы. |
| **SQLAlchemy** | ORM: позволяет работать с таблицами базы как с обычными Python-классами, не писать SQL руками. |
| **PostgreSQL** | Сама база данных, где хранятся пользователи. |
| **asyncpg** | Драйвер, через который Python асинхронно общается с PostgreSQL. |
| **Pydantic** | Проверяет и описывает форму данных (что приходит и что уходит из API). |
| **Poetry** | Менеджер зависимостей: хранит список библиотек и ставит их. |
| **Docker / docker-compose** | Упаковывает приложение и базу в «контейнеры», чтобы всё запускалось одинаково на любой машине. |
| **JWT + bcrypt** | Авторизация: bcrypt безопасно хранит пароли, JWT выдаёт «пропуск» (токен) после входа. |

### Как связаны слои

Запрос проходит их сверху вниз, и каждый слой знает только о следующем:

```
HTTP-запрос
    ↓
api/routers      принять запрос, вернуть ответ
    ↓            (не знает ни про SQL, ни про правила)
services         решить, можно ли так делать и что произойдёт
    ↓            (не знает ни про HTTP, ни про SQL)
repositories     достать и сохранить данные
    ↓            (не знает про правила)
models           таблицы базы
```

Зависимости идут только в одну сторону: роутер знает про сервис, сервис —
про репозиторий, и никогда наоборот. Благодаря этому любой слой можно
заменить или протестировать отдельно.

Быстрая проверка, что слои не перепутались:

| В файлах папки | Не должно встречаться |
|---|---|
| `api/routers/` | `select(`, `session`, `hash_password` |
| `services/` | `select(`, `from fastapi`, `HTTPException` |
| `repositories/` | бизнес-правила вида «чужое не показывать» |
| `core/` | импорты `User`, `Note` и любых других моделей |

**Почему так, а не всё в одном файле.** Пока эндпоинтов пять, разницы нет.
Но как только появляется второй вызов того же запроса, копия начинает жить
своей жизнью: в одном месте фильтр поправили, в другом забыли. Разделение
слоёв — это не красота ради красоты, а способ держать правило записанным
в одном месте.

## 4. Как это всё работает вместе

### Что происходит при `docker compose up`

1. `docker-compose.yaml` поднимает **два контейнера**: `postgres` (база) и `app` (наше приложение).
2. Сначала запускается `postgres`. Docker ждёт (`healthcheck`), пока база будет готова.
3. Затем собирается и стартует `app` по инструкции из `app.dockerfile`:
   ставится Poetry, устанавливаются библиотеки из `pyproject.toml`, копируется код.
4. Запускается команда `alembic upgrade head && uvicorn src.main:app` —
   сначала Alembic создаёт/обновляет таблицы, потом стартует веб-сервер.
5. Приложение слушает порт `8000`, который проброшен на `localhost:8000`.

### Путь одного запроса (на примере регистрации)

```
Клиент  →  POST /auth/register  →  router (auth.py)
                                     │
                    Pydantic (schemas.py) проверяет входные данные
                                     │
                    security.py хеширует пароль
                                     │
                    SQLAlchemy (models.py) сохраняет User в базу
                                     │
                    Pydantic (UserRead) формирует безопасный ответ (без пароля)
                                     ↓
Клиент  ←  JSON с id и username  ←──┘
```

## 5. Пошаговый разбор проекта: с нуля до конца

Этот раздел — главный для изучения. Читай его по порядку, сверху вниз.
Мы разберём каждый «кирпичик» приложения: **что это, зачем нужно и как
связано с остальными**. К каждому пункту указан файл, который стоит открыть.

### Шаг 0. Что вообще такое «веб-API»

Представь ресторан:

- **Клиент** — тот, кто делает запрос (браузер, мобильное приложение, `curl`).
- **Сервер (наше приложение)** — кухня, которая обрабатывает заказ.
- **API** — официант и меню: набор понятных «команд», которые клиент может
  запросить, и правил, как их запрашивать.
- **База данных** — склад продуктов, где всё хранится.

Клиент шлёт **запрос** (request), сервер возвращает **ответ** (response).
Общаются они по протоколу **HTTP**. У каждого запроса есть:

- **метод** — что мы хотим сделать: `GET` (получить), `POST` (отправить/создать),
  `PUT`/`PATCH` (изменить), `DELETE` (удалить);
- **адрес (путь)** — например `/auth/login`;
- иногда **тело** — данные (например, логин и пароль);
- **код ответа** — `200` (ок), `201` (создано), `401` (не авторизован),
  `404` (не найдено), `400` (неверный запрос) и т.д.

**Эндпоинт** — это связка «метод + путь + функция, которая это обрабатывает».
Например: `POST /auth/register` → функция `register`.

### Шаг 1. Настройки — `src/core/config.py`

**Что это.** Одно место, где приложение берёт свои параметры: адрес базы
данных, секретный ключ, срок жизни токена.

**Зачем нужно.** Пароли и адреса нельзя «зашивать» прямо в код: это небезопасно
и неудобно менять. Мы храним их в файле `.env`, а `config.py` их оттуда читает
и складывает в удобный объект `settings`.

**Как связано.** Почти все остальные файлы пишут `from src.config import settings`
и берут нужное значение, например `settings.secret_key`.

### Шаг 2. Подключение к базе — `src/core/database.py`

Здесь создаются три ключевые вещи. Разберём каждую.

- **`engine` (движок).** «Мотор», который умеет соединяться с PostgreSQL по
  адресу из настроек. Сам по себе он ничего не хранит — только открывает
  соединения, когда надо.
- **`async_session` (фабрика сессий).** **Сессия** — это одно «рабочее
  общение» с базой: в её рамках мы делаем запросы, добавляем/меняем данные,
  а потом либо сохраняем изменения (`commit`), либо отменяем. Сессию открывают
  на время одного запроса и закрывают.
- **`Base` (базовый класс).** Общий «предок» для всех таблиц. От него будут
  наследоваться модели (см. следующий шаг). По этим классам SQLAlchemy понимает,
  какие таблицы создавать.

Ещё тут есть:

- **`get_session`** — функция-«раздатчик» сессий. FastAPI будет сам вызывать её
  на каждый запрос и давать обработчику свежую сессию (это называется
  «зависимость», подробнее в шаге 6).

Таблицы создаёт **Alembic** (команда `alembic upgrade head` перед стартом
сервера), а не `create_all`. Так схему можно менять аккуратно: добавили
колонку — написали миграцию — накатили.

### Шаг 3. Модели — `src/models/` (сердце работы с данными)

**Что такое модель.** Это Python-класс, который SQLAlchemy превращает в
**таблицу** в базе данных. Простое соответствие:

```
класс   = таблица
атрибут = колонка (столбец)
объект  = одна строка (запись)
```

**Зачем это нужно (что такое ORM).** Обычно к базе обращаются на языке SQL
(`SELECT * FROM users WHERE ...`). Это отдельный язык, и писать его руками
утомительно и легко ошибиться. **ORM** (Object-Relational Mapping) — это
«переводчик»: он позволяет работать с таблицами как с обычными Python-объектами.
Ты пишешь Python-код, а SQLAlchemy сам генерирует SQL. SQLAlchemy — это ORM.

**Пример из нашего проекта.** Класс `User` описывает таблицу `users` с колонками:
`id` (номер), `username` (логин), `email` (почта), `hashed_password` (хеш пароля),
`role` (роль: user или admin), `created_at` (когда создан). Каждый
зарегистрированный человек — это одна строка в этой таблице, то есть один
объект `User`.

**Важно.** В базе мы храним НЕ пароль, а его `hashed_password` — «отпечаток»
(об этом в шаге 5).

### Шаг 4. Схемы — `src/schemas/` (форма данных API)

**Что такое схема.** Это описание того, КАК выглядят данные на «границе» API:
что клиент присылает и что мы ему возвращаем. Схемы строятся на библиотеке
**Pydantic**.

**Зачем нужно.** Схемы решают три задачи сразу:

1. **Проверка входа (валидация).** Если клиент прислал не то (забыл пароль,
   прислал число вместо строки) — FastAPI сам вернёт понятную ошибку.
2. **Формирование ответа.** Pydantic превращает наши объекты в JSON.
3. **Документация.** По схемам автоматически строится страница `/docs`.

**Почему модель и схема — это РАЗНЫЕ вещи (очень важно понять).**

- Модель (`models.py`) — как данные лежат в **базе** (там есть `hashed_password`).
- Схема (`schemas.py`) — как данные ходят через **API**.

Их специально разделяют. Пример: у нас есть схема `UserRead` для ответа, и в
ней НЕТ пароля. Поэтому наружу хеш пароля никогда не «утечёт», даже случайно.
В нашем проекте:

- `UserCreate` — что приходит при регистрации (`username` + `email` + `password`);
- `UserRead` — что отдаём наружу (`id`, `username`, `email`, `role`, без пароля);
- `RoleUpdate` — тело запроса на смену роли (`role`);
- `Token` — что отдаём при входе (сам токен).

### Шаг 5. Безопасность — `src/core/security.py` (пароли и токены)

Здесь две отдельные темы.

**1. Хеширование паролей (bcrypt).**
Пароль нельзя хранить как есть: если базу украдут, утекут все пароли.
Поэтому мы храним **хеш** — необратимый «отпечаток» пароля.

- Аналогия: хеш — как отпечаток пальца. По нему можно **проверить** человека,
  но нельзя «собрать» самого человека обратно.
- `hash_password()` — делает хеш при регистрации.
- `verify_password()` — при входе проверяет, совпадает ли введённый пароль
  с сохранённым хешем.

**2. Токены JWT.**
Было бы неудобно спрашивать логин и пароль при каждом действии. Поэтому после
входа сервер выдаёт **токен** — временный «пропуск».

- Аналогия: токен — как браслет на входе в клуб. Получил при входе, дальше
  просто показываешь охране, паспорт заново не спрашивают.
- `create_access_token()` — создаёт токен при успешном входе. Внутрь «зашиты»
  логин и срок годности; всё подписано секретным ключом, чтобы нельзя было
  подделать.
- `decode_access_token()` — проверяет токен и достаёт из него логин.

### Шаг 6. Репозитории — `src/repositories/` (единственное место с SQL)

**Что такое репозиторий.** Прослойка между приложением и базой. Остальной
код работает с ней как с коллекцией объектов: «дай пользователя с таким id»,
«посчитай, сколько подходит под фильтр». Как именно построится SQL — его
забота, и больше ничья.

**Зачем он нужен.** Раньше `select(...)` стоял прямо в обработчиках. Это
создавало три проблемы: один запрос копировался по нескольким роутерам;
правило доступа было перемешано с техникой построения запроса; проверить
логику можно было только подняв приложение целиком.

**`BaseRepository` и наследование.** Базовый класс написан один раз для
любой таблицы: `get_by_id`, `find_one`, `exists`, `count`, `find_many`,
`paginate`, `add`, `delete`, `commit`. Наследник указывает только модель:

```python
class UserRepository(BaseRepository[User]):
    model = User
    default_order_by = (User.id,)
```

После этого `await repo.get_by_id(1)` возвращает именно `User | None`, и
редактор подсказывает его поля. В `UserRepository` дописаны только запросы,
которых нет больше нигде: поиск по логину, проверка «почта занята».

**Про `Generic[ModelT]`.** `ModelT` — «переменная типа». Она запоминает, с
какой моделью работает конкретный репозиторий, чтобы подставить её в
возвращаемые значения. Без этого каждый метод возвращал бы безликий
`Base`, и толку от подсказок не было бы.

**Кто фиксирует изменения.** `add` и `delete` только готовят их — в базу
ничего не записано. Решение принимает сервис, вызывая `commit()`. Так одна
бизнес-операция остаётся одной транзакцией: если на середине что-то пойдёт
не так, в базе не останется половины изменений.

### Шаг 7. Сервисы — `src/services/` (правила продукта)

**Что такое сервис.** Слой, который отвечает на вопросы «можно ли так
делать» и «что произойдёт». Данные он берёт у репозитория, а об ошибках
сообщает исключениями из `src/core/exceptions.py`.

Пример из `AuthService.register`: проверить, не занят ли логин; понять, что
это первый пользователь, и выдать ему роль `admin`; захешировать пароль;
сохранить. Ни одного `select` и ни одного упоминания HTTP.

**Почему сервис не бросает `HTTPException`.** Потому что `HTTPException` —
понятие веба. Если сервис её бросит, он окажется привязан к HTTP, и тот же
код нельзя будет вызвать из фоновой задачи или консольной команды. Вместо
этого он бросает `ConflictError`, а слой api уже знает, что это `400`.

Короткое правило: **сервис знает, ЧТО не так; слой api знает, какой у этого
КОД ОТВЕТА.**

**Как проверить, что слой чистый.** Если в файле сервиса нет ни одного
импорта из `fastapi` и ни одного `select(...)` — всё в порядке.

### Шаг 8. Зависимости — `src/api/deps.py` (как работает «защита»)

**Что такое зависимость (Depends).** Функция, результат которой FastAPI сам
«подставляет» в обработчик. Вместо повторения подготовительного кода в
каждом эндпоинте мы говорим «мне нужно вот это».

**Что собирается в этом файле.** Цепочка слоёв:

```
get_session  →  UserRepository  →  AuthService  →  обработчик
```

Каждое звено получает предыдущее через `Depends` и не создаёт его само.
Это называется внедрением зависимостей, и польза практическая: в тесте
любое звено подменяется одной строкой `app.dependency_overrides[...]`,
без правки кода приложения. Именно так устроен `tests/conftest.py`,
подсовывающий SQLite вместо PostgreSQL.

**Главный пример — `get_current_user`.** Достаёт токен из заголовка
`Authorization: Bearer <токен>` и передаёт его `AuthService`, который
проверяет подпись, находит человека в базе и убеждается, что тот не
заблокирован. Любой обработчик, зависящий от `get_current_user`, становится
защищённым: без валидного токена FastAPI даже не войдёт в тело функции.

Рядом `get_current_admin` — проверяет `role == admin`.

```
401 Unauthorized — «кто ты?», токена нет или он испорчен
403 Forbidden    — «знаем кто, но тебе сюда нельзя»
```

**Про короткие имена.** Запись `Annotated[User, Depends(get_current_user)]`
длинная, поэтому внизу файла объявлены псевдонимы: `CurrentUser`,
`CurrentAdmin`, `UserServiceDep`, `PaginationDep`. Сигнатуры обработчиков
остаются читаемыми.

### Шаг 9. Роутеры — `src/api/routers/`

**Что такое роутер.** Группа связанных эндпоинтов в отдельном файле.
После разделения на слои в них осталось совсем немного: принять данные,
позвать сервис, вернуть ответ.

- `auth.py` — `POST /auth/register`, `POST /auth/login`;
- `users.py` — `/users/me`, список, блокировки, смена роли;
- `notes.py` — CRUD заметок.

**Про декоратор.** Строка `@router.post("/register")` над функцией — это
**декоратор**. Он привязывает функцию к адресу и методу: «когда придёт
`POST` на `/register`, вызови вот это».

**Про `src/api/errors.py`.** Здесь, в одном месте приложения, доменные
ошибки превращаются в HTTP-ответы. Формат получается одинаковым во всём
API — всегда `{"detail": "..."}`.

### Шаг 10. Сборка приложения — `src/main.py` (точка входа)

Файл намеренно короткий: он ничего не считает, только собирает приложение
из готовых частей — настройки, обработчики ошибок, роутеры, служебные
страницы `/`, `/hello` и `/health`.

Приложение создаётся функцией `create_app()`, а не прямо на уровне модуля.
Так его можно собрать несколько раз с разными настройками — например,
отдельный экземпляр на каждый тест.

Таблицы при старте **не** создаются: это делает Alembic ещё до запуска
uvicorn (см. `docker-compose.yaml`).

### Шаг 11. Собираем всё вместе: полный путь запроса

**Сценарий А — Регистрация (`POST /auth/register`)**

1. Клиент шлёт JSON `{"username": "alex", "email": "alex@example.com", "password": "12345"}`.
2. Запрос попадает в роутер `api/routers/auth.py` → функция `register`.
3. **Схема** `UserCreate` проверяет логин, почту и пароль (невалидная почта → 422).
4. **Зависимости** открывают сессию, создают `UserRepository`, а поверх него
   `AuthService` — обработчик получает готовый сервис.
5. **Сервис** спрашивает репозиторий, не заняты ли логин или почта.
   Заняты → `ConflictError`.
6. **Сервис** считает пользователей: если их ноль, роль будет `admin`.
7. **Сервис** хеширует пароль через `core/security.py`.
8. **Репозиторий** создаёт объект `User` и сохраняет (`save` = commit + refresh).
9. **Схема** `UserRead` формирует безопасный ответ — без пароля.
10. Клиент получает JSON и код `201`.

Если на шаге 5 возникла ошибка, её ловит `api/errors.py` и превращает в
ответ `400` с текстом. Сам сервис при этом про код `400` ничего не знал.

**Сценарий Б — Вход и защищённый запрос**

1. Клиент шлёт логин и пароль на `POST /auth/login`.
2. `AuthService.authenticate` находит человека и проверяет пароль
   через `verify_password`.
3. Всё верно → `create_access_token` выдаёт **токен**, клиент его сохраняет.
4. Клиент шлёт `GET /users/me` с заголовком `Authorization: Bearer <токен>`.
5. Зависимость `get_current_user` передаёт токен сервису, тот проверяет
   подпись, срок и блокировку.
6. Функция `read_me` просто возвращает полученного пользователя — всю
   работу уже сделала зависимость. Без токена был бы `401`.

Если ты понял эти два сценария — ты понял, как устроено всё приложение.
Дальше открывай файлы в порядке шагов 1–10 и читай комментарии в коде.

## 6. Как проверить авторизацию

Удобнее всего через `http://localhost:8000/docs`.

**Шаг 1. Регистрация.** Открой `POST /auth/register`, нажми *Try it out* и отправь:

```json
{ "username": "alex", "email": "alex@example.com", "password": "12345" }
```

В ответ придёт `id`, `username`, `email` и `role`. Первый пользователь в базе
получит роль `admin`, следующие — `user`.

**Шаг 2. Вход.** Нажми кнопку **Authorize** вверху страницы, введи тот же
`username` и `password`. Swagger сам вызовет `/auth/login`, получит токен и
подставит его во все запросы.

**Шаг 3. Защищённые эндпоинты.**

- `GET /users/me` — твои данные.
- `GET /users` — список всех (тоже нужен токен).
- `PATCH /users/{id}/role` с телом `{"role": "admin"}` — только если ты админ.
  Обычный пользователь получит `403 Forbidden`.

### То же самое через терминал (curl)

```bash
# Регистрация
curl -X POST http://localhost:8000/auth/register \
  -H "Content-Type: application/json" \
  -d "{\"username\": \"alex\", \"email\": \"alex@example.com\", \"password\": \"12345\"}"

# Вход — получаем токен (логин отправляется как форма!)
curl -X POST http://localhost:8000/auth/login \
  -d "username=alex&password=12345"

# Запрос к защищённому эндпоинту (подставь токен из предыдущего ответа)
curl http://localhost:8000/users/me \
  -H "Authorization: Bearer ВАШ_ТОКЕН"
```

## 7. Ключевые понятия, которые стоит запомнить

- **Модель ≠ Схема.** Модель (`models.py`) — это таблица в базе.
  Схема (`schemas.py`) — форма данных на входе/выходе API. Их разделяют,
  чтобы, например, не отдавать наружу хеш пароля.
- **Зависимости (Depends).** FastAPI умеет автоматически «подставлять» в
  обработчик нужные объекты: сессию базы (`get_session`) или текущего
  пользователя (`get_current_user`). Это и делает эндпоинт защищённым.
- **Асинхронность (`async`/`await`).** Позволяет серверу обслуживать много
  запросов одновременно, не блокируясь на ожидании ответа от базы.
- **Токен (JWT).** После входа клиент хранит токен и присылает его в заголовке
  `Authorization: Bearer <токен>`. Сервер по нему понимает, кто это, не спрашивая
  пароль каждый раз.

## 8. Полезные команды

Все команды с `docker compose` выполняются **из корня репозитория** — там
лежит `docker-compose.yaml`.

```bash
docker compose up --build      # собрать и запустить (миграции накатятся сами)
docker compose up --build -d   # то же, но в фоне
docker compose logs -f app     # смотреть логи приложения
docker compose ps -a           # статус контейнеров
docker compose down            # остановить и удалить контейнеры
docker compose down -v         # то же + удалить данные базы (чистый старт)
docker compose exec app pytest -q          # прогнать тесты
docker compose exec app alembic upgrade head
```

Без Docker — из папки `backend`, там лежат `pyproject.toml` и `alembic.ini`:

```bash
cd backend
pytest -q                      # тесты
alembic upgrade head           # накатить миграции
alembic revision --autogenerate -m "описание"
```

Зайти в базу вручную:

```bash
docker compose exec -it postgres psql -U myuser -d my_api
# внутри: \dt — список таблиц, SELECT * FROM users; — посмотреть пользователей
```

## 9. Эталон: пять задач из практики (уже сделано в коде)

Ниже — что именно реализовано, чтобы можно было сравнить со своим решением.
Код нарочно простой и хорошо прокомментирован.

### 1. Поле `email`

- Модель `User` (`src/models/user.py`): колонка `email`, уникальная, с индексом.
- Схема `UserCreate`: поле `email: EmailStr` — Pydantic сам отвергнет
  строку без `@` (ответ 422).
- Схема `UserRead`: почта отдаётся наружу, пароль — нет.
- При регистрации проверяется, что такая почта ещё не занята.

### 2. Список пользователей `GET /users`

- Эндпоинт в `src/api/routers/users.py`, логика в `src/services/user.py`.
- Зависит от `get_current_user`: без токена будет `401`.
- Роль любая — это «авторизованные», не обязательно админы.

### 3. Роли `user` / `admin`

- Перечисление `UserRole` в `src/enums.py`.
- Колонка `role` в модели. Первый зарегистрированный становится `admin`,
  остальные — `user` (удобно для учебного стенда).
- `get_current_admin` в `src/api/deps.py`: не админ → `403`.
- `PATCH /users/{id}/role` — смена роли, только для администратора.
  Себе роль менять нельзя (чтобы случайно не остаться без админа).

Разница кодов, которую стоит запомнить:

- `401 Unauthorized` — нет или плохой токен («кто ты?»);
- `403 Forbidden` — токен есть, прав не хватает («тебе нельзя»).

### 4. Alembic вместо `init_db`

- Папка `alembic/` + файл `alembic.ini`.
- Первая миграция: `alembic/versions/0001_create_users.py`.
- `docker-compose.yaml` перед запуском сервера делает `alembic upgrade head`.
- `src/core/database.py` больше не вызывает `create_all`.

Если база осталась со **старой** схемой (без `email`/`role`), проще начать
чисто: `docker compose down -v` и снова `docker compose up --build`.

Новая миграция после изменения моделей:

```bash
docker compose exec app alembic revision --autogenerate -m "описание"
docker compose exec app alembic upgrade head
```

### 5. Тесты pytest

- `tests/conftest.py` — SQLite в памяти, чтобы тесты не требовали Docker.
- `tests/test_auth.py` — регистрация (успех, дубли логина/почты, плохая почта)
  и вход (успех, неверный пароль, несуществующий логин).
- `tests/test_users.py` — список только с токеном, 403 для обычного пользователя,
  админ может сменить роль.

Запуск:

```bash
docker compose exec app pytest -q
```

или локально, если зависимости установлены: `cd backend && pytest -q`
(короткая команда из корня — `make test-local`).

## 10. Следующие 5 задач (эталон уже в коде)

Это продолжение практики. Сложность растёт: каждая задача опирается на предыдущие.
Ниже — формулировки, как их давали «на самостоятельную работу», и где лежит эталон.

Правила:
- не ломай уже работающие эндпоинты;
- новые колонки и таблицы — только через **Alembic**, не через `create_all`;
- в ответах по-прежнему нет пароля и хеша;
- в `/docs` всё должно быть понятно без подсказок снаружи.

### Задача 6. Пагинация и поиск в списке пользователей

**Зачем.** Научиться принимать **query-параметры** (`?limit=10&offset=0&q=al`)
и не отдавать всю базу разом.

**Что сделать.** Доработать `GET /users`:

- `limit` — сколько записей вернуть (по умолчанию 20, максимум 100);
- `offset` — сколько записей пропустить (для «второй страницы»);
- `q` — необязательная строка: фильтр по `username` или `email` (подстрока,
  без учёта регистра).

Ответ лучше сделать не голым списком, а объектом:

```json
{
  "items": [ { "id": 1, "username": "alex", "email": "...", "role": "admin" } ],
  "total": 42,
  "limit": 20,
  "offset": 0
}
```

`total` — сколько пользователей подошло под фильтр **всего**, не только
на этой странице.

**Как проверить.** Без токена — 401. `limit=1` возвращает одного человека,
`offset=1` — следующего. Поиск `q=alex` не показывает «bob». Невалидный
`limit=0` или `limit=9999` — ошибка 422.

**Подсказка.** В FastAPI параметры функции становятся query-параметрами.
В SQLAlchemy: `ilike`, `limit()`, `offset()`, отдельно `func.count()`.

### Задача 7. Обновление своего профиля

**Зачем.** Научиться менять уже существующую строку в базе (`UPDATE`), а не
только создавать.

**Что сделать.** Эндпоинт `PATCH /users/me`. Можно менять `username` и/или
`email`. Пароль и роль сюда не входят.

- Нужен токен. Чужой профиль через этот адрес менять нельзя — только свой.
- Если поле не прислали — оно не меняется (частичное обновление).
- Новый логин/почта не должны совпадать с чужими → 400.
- Невалидная почта → 422.

**Как проверить.** Залогинься, смени почту, снова вызови `GET /users/me` —
там уже новое значение. Попытка занять чужой email — 400.

**Подсказка.** Схема с необязательными полями: `username: str | None = None`.
В обработчике обновляй только то, что не `None`. Не забудь `commit` и `refresh`.

### Задача 8. Смена пароля

**Зачем.** Закрепить хеширование: старый пароль проверяем, новый сразу
хешируем, открытый текст нигде не светится.

**Что сделать.** `POST /users/me/password` с телом:

```json
{ "old_password": "12345", "new_password": "abcdef" }
```

- Нужен токен.
- Неверный старый пароль → 400 (не 401: человек уже вошёл, ошибся в старом).
- Новый короче 5 символов → 422.
- После смены вход со **старым** паролем не работает, с новым — работает.

**Как проверить.** Смени пароль → логин со старым даёт 401, с новым выдаёт токен.

**Подсказка.** `verify_password` + `hash_password` из `security.py`.
В ответе достаточно `{"detail": "Пароль обновлён"}` — новый пароль не возвращай.

### Задача 9. Блокировка пользователя (`is_active`)

**Зачем.** Связать новую колонку, миграцию, проверку при входе и проверку
в `get_current_user`. Это уже маленький «жизненный цикл» аккаунта.

**Что сделать.**

1. Колонка `is_active: bool` у `User`, по умолчанию `true`.
2. Миграция Alembic (не правь руками старую `0001_*` — сделай **новую**).
3. Заблокированный не может войти (`POST /auth/login` → 403 и понятный текст).
4. Если админ заблокировал человека **уже с токеном**, следующие запросы
   этого человека тоже 403 (проверку добавь в `get_current_user`).
5. Эндпоинты только для админа:
   - `POST /users/{id}/block`
   - `POST /users/{id}/unblock`
6. Админ не может заблокировать **себя**.
7. В `UserRead` поле `is_active` видно.

**Как проверить.** Админ блокирует bob → bob не логинится. Разблокировка
возвращает доступ. Обычный пользователь на `/block` получает 403.

**Подсказка.** `alembic revision --autogenerate -m "add is_active to users"`,
потом `alembic upgrade head`. Для уже существующих строк в миграции поставь
`server_default=true`, иначе PostgreSQL не даст добавить NOT NULL колонку.

### Задача 10. Заметки пользователя (новая таблица и связь)

**Зачем.** Первый **relation**: один пользователь — много заметок.
Новая модель, внешний ключ, отдельные схемы и роутер. Самая объёмная задача.

**Что сделать.** Модель `Note`: `id`, `title`, `body`, `owner_id` (FK на `users.id`),
`created_at`. Своя миграция.

Эндпоинты:

- `POST /notes` — создать свою заметку (токен обязателен, `owner_id` берётся
  из текущего пользователя, клиент его не присылает);
- `GET /notes` — список **своих** заметок (с пагинацией, как в задаче 6);
- `GET /notes/{id}` — одна заметка; чужую обычный пользователь не видит → 404
  (не 403: не выдаём, что заметка существует);
- `PATCH /notes/{id}` — править только свою;
- `DELETE /notes/{id}` — удалить только свою.

Админ может читать **любые** заметки (`GET /notes?all=true` или отдельный
`GET /notes/all` — выбери один вариант и опиши в `/docs`).
Удалять чужие админу можно, это полезно для модерации.

**Как проверить.** Два пользователя: каждый видит только свои заметки.
Попытка открыть чужой id — 404. Админ с флагом видит все. После `DELETE`
`GET` той же заметки — 404.

**Подсказка.** В модели User: `notes: Mapped[list["Note"]] = relationship(...)`.
В Note: `owner_id: Mapped[int] = mapped_column(ForeignKey("users.id"))`.
Новый файл `src/api/routers/notes.py` и подключение в `src/api/router.py`.
Не забудь импортировать `Note` в `alembic/env.py` (или в `models.py`), иначе
Alembic «не увидит» таблицу.

### Задача 11. Refresh-токен и выход

**Зачем.** Access-токен живёт долго (сейчас 60 минут) и его нельзя отозвать:
пока срок не вышел, заблокировать сессию нельзя. В нормальных API два токена:
короткий access и длинный refresh, который можно инвалидировать.

**Что сделать.**

1. Access живёт **15 минут** (вынеси в настройки). Refresh — **7 дней**.
2. Таблица `refresh_tokens`: `id`, `user_id`, `token_hash` (хеш, не сам токен),
   `expires_at`, `revoked_at` (nullable), `created_at`.
3. `POST /auth/login` отдаёт оба токена:
   ```json
   { "access_token": "...", "refresh_token": "...", "token_type": "bearer" }
   ```
4. `POST /auth/refresh` принимает refresh и выдаёт **новую пару**.
   Старый refresh после этого недействителен (ротация: украденный старый
   токен больше не продлевается).
5. `POST /auth/logout` принимает refresh и помечает его отозванным.
   Повторный refresh этим токеном → 401.
6. В базе храни только хеш refresh (как пароль). Сам токен — только клиенту.
7. Заблокированный пользователь не может обновить токен (403).

**Как проверить.** Логин → refresh работает один раз, второй раз со старым
refresh — 401. Logout → refresh больше не работает. В ответе API и в базе
нет открытого refresh-токена.

**Подсказка.** Генерируй случайную строку (`secrets.token_urlsafe`), в базу
клади `hash_password` или sha256. Срок смотри по `expires_at`, не только по JWT.
Access по-прежнему JWT с `sub = id`.

### Задача 12. Теги у заметок (многие-ко-многим)

**Зачем.** Заметки и теги — не «один ко многим». Один тег на многих заметках,
у заметки несколько тегов. Это связь **many-to-many** и промежуточная таблица.

**Что сделать.**

1. Модель `Tag`: `id`, `name` (уникальное, храни в нижнем регистре).
2. Таблица связи `note_tags` (`note_id`, `tag_id`, составной первичный ключ).
3. При создании и правке заметки можно передать `tags: ["work", "idea"]`.
   Тега нет — создай. `"Work"` и `"work"` — один и тот же тег.
4. `GET /notes?tag=work` — только свои заметки с этим тегом
   (у админа с `all=true` — все такие).
5. `GET /tags` — теги, которые встречаются **на заметках текущего пользователя**
   (админ с `?all=true` видит все). С пагинацией не обязательно, но отсортируй по имени.
6. В `NoteRead` поле `tags: list[str]`.

Пустой список `tags: []` при `PATCH` **снимает** все теги. Поле не прислали —
теги не трогай.

**Как проверить.** Две заметки с общим тегом `work`. Фильтр возвращает обе
свои и не возвращает чужую. `"Work"` не плодит второй тег в базе.

**Подсказка.** `relationship` с `secondary="note_tags"`. Не отдавай клиенту
id связи — только имена. Удаление заметки не должно удалять сам тег,
если он ещё висит на других.

### Задача 13. Мягкое удаление заметок

**Зачем.** `DELETE` сейчас стирает строку навсегда. В продуктах чаще ставят
`deleted_at`: заметка «в корзине», её можно вернуть, обычные списки её не видят.

**Что сделать.**

1. Колонка `notes.deleted_at` (nullable datetime). Новая миграция.
2. `DELETE /notes/{id}` не делает `session.delete`, а ставит `deleted_at = now()`.
   Повторный DELETE уже удалённой — 404.
3. `GET /notes`, `GET /notes/{id}`, `PATCH` **не видят** удалённые
   (для обычного пользователя — как будто их нет, 404).
4. `POST /notes/{id}/restore` — владелец возвращает свою заметку
   (`deleted_at = null`). Чужую восстановить нельзя (404).
   Админ чужие тоже не восстанавливает — только владелец.
5. `GET /notes?deleted=true` — корзина **только своих**.
   Админский `all=true` по-прежнему **без** удалённых, если не передан `deleted=true`.
6. Жёсткое удаление: `DELETE /notes/{id}/permanent` — только админ,
   строка реально удаляется. Обычный пользователь → 403.

**Как проверить.** Удалил → пропала из списка → restore → снова есть.
Чужой `GET` удалённой — 404, не 410 и не «это чужое». Фильтр по тегу
не показывает удалённые.

**Подсказка.** Один хелпер `_visible_notes(user, *, deleted: bool)`, чтобы
не забыть фильтр `deleted_at IS NULL` в пяти местах.

### Задача 14. Журнал действий

**Зачем.** Кто заблокировал, кто сменил роль, кто удалил заметку — это уже
не поле на пользователе, а отдельная история. Её нельзя «поправить задним числом»
из обычного API.

**Что сделать.**

1. Таблица `audit_logs`: `id`, `actor_id` (FK, nullable — вдруг система),
   `action` (строка, например `user.blocked`), `entity` (`user` / `note`),
   `entity_id`, `payload` (JSON, только безопасные поля), `created_at`.
2. Пиши запись при:
   - смене роли;
   - block / unblock;
   - создании, мягком удалении, восстановлении и жёстком удалении заметки;
   - смене пароля (**без** старого и нового пароля в payload).
3. `GET /audit` — только админ. Пагинация как у `/users`:
   `limit`, `offset`, фильтры `action` и `actor_id`.
4. Обычный пользователь на `/audit` → 403. Чужие логи править и удалять
   нельзя: эндпоинтов изменения журнала нет.
5. Если действие не удалось (403/400) — записи в журнале **нет**.

**Как проверить.** Админ блокирует bob → в журнале одна строка
`user.blocked`, в payload есть `user_id` боба, нет паролей. Bob на `/audit`
получает 403. Смена пароля не кладёт пароль в JSON.

**Подсказка.** Не пиши лог «вслепую» в каждом роутере копипастой без коммита.
Удобно: функция `write_audit(session, ...)` в том же `session`, что и само
изменение, один `commit` на оба. Иначе при ошибке останется лог о том,
чего не случилось.

### Задача 15. Файл к заметке

**Зачем.** До этого API принимал только JSON. Файл — это другой тип запроса
(`multipart/form-data`), байты на диске и проверка, что чужой файл не скачать
по угаданному пути.

**Что сделать.**

1. Таблица `attachments`: `id`, `note_id`, `filename` (как назвал клиент,
   только имя, без пути), `stored_name` (случайное имя на диске),
   `content_type`, `size`, `created_at`.
2. `POST /notes/{id}/attachments` — `UploadFile`. Лимит **1 МБ**.
   Разрешены только `text/plain`, `image/png`, `image/jpeg`, `application/pdf`.
   Иначе 415 или 400. К чужой заметке — 404. К удалённой — 404.
3. Файлы лежат в папке `uploads/` **вне** корня раздачи статики.
   Имя на диске — `uuid`, не оригинальное: иначе `../../.env` прочитает чужое.
4. `GET /notes/{id}/attachments/{attachment_id}` — скачивание.
   Видит тот, кто видит заметку (владелец или админ). Чужой — 404.
5. `DELETE` вложения — владелец или админ. Файл с диска тоже удаляется.
6. Жёсткое удаление заметки удаляет и файлы. Мягкое — нет: после restore
   вложения на месте.
7. В Docker смонтируй volume на `uploads/`, чтобы файлы пережили перезапуск
   контейнера.

**Как проверить.** Залил png → скачал те же байты. Залил `.exe` или 2 МБ — отказ.
Bob не скачивает файл Алекса (404). В URL нет `../`. После permanent delete
файла на диске нет.

**Подсказка.** `python-multipart` уже стоит. Ответ на скачивание —
`FileResponse` или `StreamingResponse` с `Content-Disposition`.
Оригинальное имя прогоняй через безопасную функцию: убери путь, оставь basename.

---

Порядок: 11 (безопасность сессии) → 12 (связь таблиц) → 13 (состояние записи)
→ 14 (история, её проще вешать, когда delete/restore уже есть) → 15 (файлы).
11 и 15 самые «взрослые»: там легко ошибиться с безопасностью.

## 14. Частые вопросы (FAQ)

**Почему база называется `postgres` в строке подключения, а не `localhost`?**
Внутри Docker каждый сервис виден по своему имени из `docker-compose.yaml`.
Приложение и база — в одной сети, поэтому приложение обращается к базе
по имени сервиса `postgres`. С твоего компьютера та же база доступна по
`localhost` (порт задан в `.env` через `POSTGRES_PORT`).

**Где физически хранятся данные? Пропадут ли они после перезапуска?**
Данные лежат в Docker-томе `postgres_data` (см. `docker-compose.yaml`).
После `docker compose down` они сохраняются. Чтобы удалить их и начать
с чистой базы — используй `docker compose down -v`.

**Я изменил код — надо ли перезапускать?**
Сервер запущен с флагом `--reload`, поэтому при изменении Python-файлов
приложение перезапускается само. Если менял зависимости в `pyproject.toml`
или сам `Dockerfile` — нужна пересборка: `docker compose up --build`.

**Что такое `/docs` и `/redoc`?**
Это автоматически сгенерированная документация API.
`/docs` (Swagger UI) — интерактивная, можно нажимать кнопки и вызывать методы.
`/redoc` — тот же список эндпоинтов, но в виде красивой статичной странички.

**После обновления код падает на старте (ошибка про колонку email/role)?**
Старая база создавалась без этих колонок. Alembic видит таблицу `users`
и не может «создать её заново». Для учебного проекта проще снести том:

```bash
docker compose down -v
docker compose up --build
```
