## Что исправить в первую очередь

### 1. Прочитан только первый лист Excel

`read_table` вызывает `pd.read_excel(path)` без параметров, а такой вызов
берёт только первый лист «Year 2009-2010». Поэтому:

- когорты заканчиваются на 2010-12;
- BTYD обучается на 9 месяцах вместо 18;
- для оттока есть всего 7 срезов.

Исправлять нужно в `backend/src/analytics/ingest.py`, а не в ноутбуках:
`pd.read_excel(path, sheet_name=None)` возвращает словарь листов, их нужно
склеить через `pd.concat`. Листы этого датасета перекрываются в начале
декабря 2010, поэтому после склейки обязателен `drop_duplicates`.

### 2. Ошибка в правдоподобии BG/NBD

У клиентов без повторных покупок слагаемое `r·ln α` учитывается дважды:
`A1` уже содержит `r * log(alpha)`, а затем прибавляется
`r * log(alpha / (alpha + T))`. Из-за этого оптимизатор раздувает параметры,
и они упираются в границы: в выводе `r=100, alpha=200` ровно совпадают
с верхними пределами `bounds`.

Проверено на синтетических данных с известными параметрами
(r=0.8, α=40, a=0.6, b=2.5): текущая формула уходит в бесконечность,
исправленная восстанавливает ≈(0.81, 42.0, 0.66, 2.65).

Правильно для x=0: `A1 + log_term1`. Весь случай можно записать одной строкой:

```python
ll = A1 + A2 + np.logaddexp(log_term1, np.where(x > 0, log_term2, -np.inf))
```

### 3. Ещё две ошибки в `04_btyd` — из-за них прогноз занижен на 52%

- **Monetary считается как средняя строка чека** (около 18 у.е.), а должен
  быть средний заказ. Сначала свернуть строки в покупки по клиенту и дню,
  потом брать среднее по повторным покупкам.
- **Прогноз покупок линеен по времени:** `CLV_365 / CLV_90` равно ровно
  365/90 у каждого клиента. Это не формула BG/NBD. Правильное условное
  ожидание (Fader, Hardie, Lee, 2005, уравнение 10):

  ```
  E[Y(t)] = (a+b+x−1)/(a−1)
            · [1 − ((α+T)/(α+T+t))^(r+x) · ₂F₁(r+x, b+x; a+b+x−1; t/(α+T+t))]
            / [1 + δ(x>0) · a/(b+x−1) · ((α+T)/(α+tₓ))^(r+x)]
  ```

  `hyp2f1` в ноутбуке уже импортирована, но не используется.

### 4. Утечка из будущего в оттоке

Окна таргета последних обучающих срезов залезают в тестовый период. Например,
срез 2010-07-29 смотрит на покупки до 2010-10-27, а тестовый срез начинается
2010-08-28. Нужен зазор длиной `CHURN_DAYS`:

```python
train_slices = [
    s for s in slice_dates[:-1]
    if s + pd.Timedelta(days=CHURN_DAYS) <= test_slice
]
```

### 5. Давно ушедшие клиенты в выборке оттока

Из-за них метрики завышены, а топ-5 по риску — люди, которые не покупали уже
259–269 дней. Отделу удержания такой список бесполезен. Оставлять в срезе
только активную базу, например клиентов с покупкой за последние 180 дней.

## Что ещё не дотягивает до критериев «готово»

**2.2 — RFM**

- Клиент с высоким R (купил недавно) и F=2 ни под одно правило не подходит
  и попадает в «Потерянные». Проверка:
  `rfm_user.query("R >= 4 and Segment == 'Потерянные'")`.
- `rank(method='first')` раздаёт одинаковым клиентам баллы F=1 или F=2
  в зависимости от порядка строк в файле. Для частоты лучше фиксированные
  пороги: `pd.cut(Frequency, bins=[0, 1, 2, 4, 9, np.inf])`.
- Колонка «Средний_чек» на самом деле считает среднюю выручку на клиента,
  а не чек. Чек = выручка сегмента / число заказов сегмента.
- Чеки-возвраты попадают во Frequency — частоту считать по `amount > 0`.

**2.3 — когорты**

- Когорта 2009-12 — это не новые клиенты, а вся база, накопленная до начала
  выгрузки (1045 человек против 250–450 в остальных). Из-за неё сравнение
  «старые против новых» получается смещённым.
- Последний месяц неполный, поэтому крайние правые клетки занижены.
- Сравнение средним по столбцам некорректно: на больших возрастах «новые»
  представлены одной-двумя когортами. Лучше зафиксировать возраст (M1, M3)
  и смотреть его по месяцу когорты.
- Вывод о том, живут ли новые когорты дольше, словами нигде не записан.

**2.4 — BTYD**

- Нет сверки с `lifetimes` (если не встаёт на numpy 2 — отдельное окружение
  или `pymc_marketing.clv.BetaGeoModel`).
- Обучение идёт не на 18 месяцах.
- MAE не с чем сравнить: нужна наивная базовая линия.

**2.6 — калибровка и объяснимость**

- Проверка «среди оценки 0.7 уходит примерно 70%» есть только на графике,
  числом нигде не выведена. Нужна таблица по корзинам и `brier_score_loss`.
- SHAP объясняет `lgb_model`, а вероятность берётся из другой, калиброванной
  модели. Решение: калибровать поверх одной обученной модели на отдельном
  временном срезе (`cv="prefit"` или `FrozenEstimator`).
- В причины риска попадают признаки с отрицательным SHAP; половина причин
  звучит как «Фактор 'monetary' имеет неоптимальное значение».
